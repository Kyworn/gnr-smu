# Ryzen 9 9950X3D telemetry profile

The Ryzen 9 9950X3D exposes PM table version `0x620205`, with 2452 bytes / 613
little-endian float32 values. This is not the 1828-byte / 457-float table used by
the 9800X3D. The hardware gate therefore matches all of CPU model, PM version,
table size and physical core count before enabling named telemetry.

## Per-core layout

| Metric | Float indices | Count |
|---|---:|---:|
| Core power / power-related metric | `301..316` | 16 |
| Core voltage | `317..332` | 16 |
| **Core temperature (direct °C)** | **`333..348`** | **16** |
| Core FIT / related metric | `349..364` | 16 |
| Core effective/activity-related metric | `365..380` | 16 |
| Core C0 residency (%) | `381..396` | 16 |
| Core CC1 residency (%) | `397..412` | 16 |
| Core CC6 residency (%) | `413..428` | 16 |
| Per-core boost-limit candidate (GHz) | `445..460` | 16 |

No PM-table block is currently established as the 9950X3D's live per-core
frequency. The GUI therefore reads live frequency from Linux `cpufreq` instead of
mislabeling `d[349..364]`. The `d[461..476]` block stays essentially constant and is
not treated as live frequency either.

The GUI also exposes the explicitly mapped 0x620205 clocks and voltage rails:

| Metric | Float index |
|---|---:|
| VDD_MISC | `58` |
| FCLK / UCLK / MCLK | `71` / `75` / `79` |
| VDDCR_SOC | `83` |
| CLDO_VDDG_IOD / CLDO_VDDG_CCD | `259` / `261` |
| CLDO_VDDP | `269` |

The dashboard's **System, Rails & L3** section also makes the following
low-confidence candidates available for research and comparison. Their table
position was originally assumed to be L3-related, but that identity is **not
confirmed** — the names below describe only what was actually measured:

| Candidate | CCD 0 / CCD 1 float indices | Notes |
|---|---:|---|
| CCD L3 temperature? | `595` / `596` | CCD-selective: idle ~Core-avg + 0.5 K, confirmed by a live per-CCD load test to rise selectively with its own CCD (+13.8 K on CCD0 when only CCD0 is loaded, vs +6.5 K on CCD1's lane in the same run, and reversed when CCD1 is loaded instead). A separate ALU-vs-cache-thrash comparison found it rises 3-6x more per K of core-temp rise under L3 cache-thrash load than under pure-ALU load — suggestive of L3 coupling, but not proof (single run, confounded by very different absolute core temperatures between the two loads). Renamed from "diode temperature" (2026-08-25): that name was an unjustified guess about the sensor's physical type, not something ever measured. |
| CCD shared temperature? | `611` / `612` | Idle ~36 °C, but the per-CCD load test shows both `d[611]` and `d[612]` rise almost identically (±0.2 K of each other) no matter which CCD is loaded — it is *not* per-CCD. Under the cache-thrash test, this pair also showed a disproportionate rise like the CCD-selective pair did, so it is not simply "the HWiNFO L3 lane" either. Removed from the GUI (2026-08-25): confirmed non-selective, not a per-CCD value. |

`d[589]`/`d[590]` ("CCD power") and `d[591]`/`d[592]` ("CCD VDDM power") were
checked the same way (busy-loop load pinned to CCD0 only, then CCD1 only) on
2026-08-25: both lanes of each pair rose almost identically regardless of
which CCD was loaded (e.g. `d[589]`/`d[590]` +3.68/+3.14 W under CCD0 load vs
+3.84/+3.69 W under CCD1 load), unlike the correctly-selective `d[595]`/
`d[596]` sanity check run in the same session. They are **not** per-CCD power
values and have been removed from the GUI; kept only as raw research fields
in `HardwareProfile`.

These values are deliberately marked with a `?`, their raw `d[index]`, and an
experimental warning. They are not presented as established telemetry. The
dashboard also shows the independent Linux `k10temp` `Tccd1` / `Tccd2` readings
beside the temperature candidates so that differences are visible rather than
hidden. The HWiNFO-style sensor table retains a current, minimum, maximum and
average for every numeric value until it is reset. The dashboard also shows a
live "CPU EDC" candidate, `d[64]`, next to the confirmed EDC limit (`d[63]`):
idle ~7 A, rising to ~128 A under all-core `stress-ng` load while staying above
the same run's TDC current (`d[9]`, ~108 A) as a real peak-current reading
should (`research/recheck_edc.py`). It is labeled as a live PM-table candidate,
not yet SMU-confirmed.

**Is this actually L3 telemetry?** Partially supported now, still not fully proven. Three live tests were run:

1. `research/recheck_l3.py` loaded each CCD individually with a pinned worker
   and watched `d[595]/d[596]/d[611]/d[612]`: loading CCD0 alone raised
   `d[595]` by +13.8 K but `d[596]` by only +6.5 K over the same baseline;
   loading CCD1 alone reversed that (`d[596]` +12.8 K vs `d[595]` +6.6 K).
   `d[595]`/`d[596]` therefore selectively track their own CCD; `d[611]`/
   `d[612]` moved almost identically to each other regardless of which CCD
   was loaded. This only proves **CCD affinity** — a generic per-CCD hotspot
   sensor unrelated to the cache would show the exact same pattern.
2. `research/l3_specificity.py` compared an ALU-only load (`stress-ng
   --cpu-method ackermann`, tiny working set, low L3 traffic) against an
   L3-cache-thrash load (`stress-ng --cache --cache-level 3`), both pinned to
   CCD0 only. Relative to CCD0's average core-temp rise, the cache-thrash load
   moved every one of the four candidate lanes 3-6x more than the ALU load did
   (e.g. `d[595]` rose by x1.54 of the core-temp rise under cache-thrash vs
   only x0.43 under ALU load). That is *suggestive* of L3-traffic coupling,
   but it was a single, uncontrolled run: the ALU load happened to drive core
   temperatures far higher in absolute terms (~69 °C avg) than the cache load
   (~41 °C avg), and the cache-thrash run also broke `d[595]`/`d[596]`'s
   CCD-selectivity (both lanes rose almost equally even though only CCD0 was
   loaded) — an anomaly that needed repeat, controlled testing (matched core
   power/temperature between load types) before any "L3" label could be
   considered confirmed.
3. `research/l3_specificity_controlled.py` repeated the comparison with that
   confound removed: the ALU load was throttled with `stress-ng --cpu-load`
   (duty-cycle limiting) until its CCD0-avg core-temp rise matched the
   cache-thrash run's rise to within 0.44 K (+9.99 K ALU vs +9.55 K cache).
   At that *matched* core-temp rise, `d[595]` still rose an extra +4.2 K and
   `d[596]` an extra +7.9 K under cache-thrash compared to ALU load — an
   excess that core heating cannot explain, and is genuine evidence of
   L3-traffic coupling for this pair. `d[611]`/`d[612]` did the *opposite*:
   they rose 2.7 K *less* under cache-thrash than under ALU load at the same
   core-temp rise, which rules out an L3-cache identity for that pair — it is
   tracking something else (general fabric/package heat, not cache traffic).

This was a single controlled run; a repeat would strengthen confidence
further. But the result is a clean, confound-free split: `d[595]`/`d[596]`
now have real (if not yet fully proven) evidence of L3 coupling, while
`d[611]`/`d[612]` have evidence *against* an L3 identity. The profile fields
keep their honest names (`ccd_l3_temperature`, `ccd_shared_temperature`,
`ccd_power_candidate`, `ccd_vddm_candidate`) rather than being re-labeled
"L3" outright, pending a confirming second run.

The temperature block was checked independently on both CCDs with a single pinned
busy worker. Loading core 0 made `d[333]` the hottest lane; loading core 8 made
`d[341]` the hottest lane. Both rose by about 20 °C, while `k10temp` independently
reported the corresponding CCD as the hot CCD (`Tccd1` for core 0, `Tccd2` for core
8). This establishes both the field identity and lane ordering.

The check is reproducible with:

```bash
python3 tools/validate_core_temps.py
```

## SMU write profile

The 9950X3D GUI uses the Granite Ridge/Zen 5 command profile from
[ZenStates-Core's Zen 5 settings](https://github.com/irusanov/ZenStates-Core/blob/master/SMUSettings/Zen5Settings.cs),
which inherit the
[Zen 4 command table](https://github.com/irusanov/ZenStates-Core/blob/master/SMUSettings/Zen4Settings.cs):

| Control | MP1 message | Argument |
|---|---:|---|
| PPT / fast limit | `0x3E` | mW |
| TDC | `0x3C` | mA |
| EDC | `0x3D` | mA |
| Per-core Curve Optimizer | `0x35` | CCD/core mask plus signed 16-bit margin |

The command sender rejects any message outside the profile allowlist. In particular,
it never uses `0x58+` for cores 8-15; core selection is encoded into the argument to
`0x35`, matching
[SetPsmMarginSingleCore](https://github.com/irusanov/ZenStates-Core/blob/master/SMUCommands/SetPsmMarginSingleCore.cs).
The existing control dialogs and CLI workflow are unchanged.

These settings are volatile and reset on reboot. Negative Curve Optimizer values can
still cause computational instability or a crash; no software can guarantee a given
silicon sample is stable at a requested undervolt.
