# Ryzen 9 9950X3D telemetry profile

The Ryzen 9 9950X3D exposes PM table version `0x620205`, with 2452 bytes / 613
little-endian float32 values. This is not the 1828-byte / 457-float table used by
the 9800X3D. The hardware gate therefore matches all of CPU model, PM version,
table size and physical core count before enabling named telemetry.

## Per-core layout

| Metric | Float indices | Count |
|---|---:|---:|
| Core power / power-related metric | `301..316` | 16 |
| Core voltage | `317..332` | 16 |
| **Core temperature (direct °C)** | **`333..348`** | **16** |
| Core FIT / related metric | `349..364` | 16 |
| Core effective/activity-related metric | `365..380` | 16 |
| Core C0 residency (%) | `381..396` | 16 |
| Core CC1 residency (%) | `397..412` | 16 |
| Core CC6 residency (%) | `413..428` | 16 |
| Per-core boost-limit candidate (GHz) | `445..460` | 16 |

No PM-table block is currently established as the 9950X3D's live per-core
frequency. The GUI therefore reads live frequency from Linux `cpufreq` instead of
mislabeling `d[349..364]`. The `d[461..476]` block stays essentially constant and is
not treated as live frequency either.

The GUI also exposes the explicitly mapped 0x620205 clocks and voltage rails:

| Metric | Float index |
|---|---:|
| VDD_MISC | `58` |
| FCLK / UCLK / MCLK | `71` / `75` / `79` |
| VDDCR_SOC | `83` |
| CLDO_VDDG_IOD / CLDO_VDDG_CCD | `259` / `261` |
| CLDO_VDDP | `269` |

The dashboard's **System, Rails & L3** section also makes the following
low-confidence candidates available for research and comparison:

| Candidate | CCD 0 / CCD 1 float indices |
|---|---:|
| L3 logic power | `589` / `590` |
| L3 VDDM power | `591` / `592` |
| L3 temperature | `595` / `596` |

These values are deliberately marked with a question mark, their raw `d[index]`, and
an experimental warning. They are not presented as established telemetry. The
dashboard also shows the independent Linux `k10temp` `Tccd1` / `Tccd2` readings beside the
temperature candidates so that differences are visible rather than hidden. The
HWiNFO-style sensor table retains a current, minimum, maximum and average for every
numeric value until it is reset. The low-confidence EDC-live candidate remains
undisplayed.

The temperature block was checked independently on both CCDs with a single pinned
busy worker. Loading core 0 made `d[333]` the hottest lane; loading core 8 made
`d[341]` the hottest lane. Both rose by about 20 °C, while `k10temp` independently
reported the corresponding CCD as the hot CCD (`Tccd1` for core 0, `Tccd2` for core
8). This establishes both the field identity and lane ordering.

The check is reproducible with:

```bash
python3 tools/validate_core_temps.py
```

## SMU write profile

The 9950X3D GUI uses the Granite Ridge/Zen 5 command profile from
[ZenStates-Core's Zen 5 settings](https://github.com/irusanov/ZenStates-Core/blob/master/SMUSettings/Zen5Settings.cs),
which inherit the
[Zen 4 command table](https://github.com/irusanov/ZenStates-Core/blob/master/SMUSettings/Zen4Settings.cs):

| Control | MP1 message | Argument |
|---|---:|---|
| PPT / fast limit | `0x3E` | mW |
| TDC | `0x3C` | mA |
| EDC | `0x3D` | mA |
| Per-core Curve Optimizer | `0x35` | CCD/core mask plus signed 16-bit margin |

The command sender rejects any message outside the profile allowlist. In particular,
it never uses `0x58+` for cores 8-15; core selection is encoded into the argument to
`0x35`, matching
[SetPsmMarginSingleCore](https://github.com/irusanov/ZenStates-Core/blob/master/SMUCommands/SetPsmMarginSingleCore.cs).
The existing control dialogs and CLI workflow are unchanged.

These settings are volatile and reset on reboot. Negative Curve Optimizer values can
still cause computational instability or a crash; no software can guarantee a given
silicon sample is stable at a requested undervolt.
