# Ryzen 5 9600X telemetry and SMU control profile

The Ryzen 5 9600X shares PM table version `0x620105` and the full 1828-byte /
457-float layout with the 9800X3D — a real data point, not an assumption: a
`tools/submit_dump.py` bundle from a physical 9600X (2026-09-12) confirmed both
the version and the size before any offset was reused. The hardware gate still
matches CPU model, PM version, table size *and* physical core count (6, not 8)
before selecting this profile, so a future part that also happens to share the
table can never be silently mapped onto the 9600X's fused-core layout.

The two raw snapshots from that bundle (one idle, one `--with-load` all-core)
live in `tests/fixtures/granite_ridge/9600x/`, the same treatment the 5600X's
dump got in `tests/fixtures/vermeer/`, and are exercised by
`tests/test_hwgate_9600x.py`: detection, the slot table, fused-slot zero
signatures on both real snapshots, `_fused_layout_matches()` against real
bytes, and structural sanity ranges on `tctl`/`ccd_l3_temperature`.

## Fused-core layout

The 9600X is a 6-core, single-CCD part on an 8-slot table. `detect_active_slots()`
on the core-power (`d[333..340]`) and core-voltage (`d[309..316]`) blocks, at
both idle and under `--with-load` all-core stress, consistently showed:

- **Active SMU slots:** `(0, 1, 2, 3, 6, 7)`
- **Fused slots:** `(4, 5)`

`core_slots=(0, 1, 2, 3, 6, 7)` in `gnr_smu/profiles.py` encodes this — Linux
cores 4 and 5 live on SMU slots 6 and 7. Like the 5600X profile, this layout is
re-verified against the live table at detection time
(`_fused_layout_matches()`) rather than trusted blindly; a differently-binned
9600X sample would refuse rather than mislabel cores.

## Telemetry confidence

Every per-core and global offset is inherited from the 9800X3D map on the
strength of the identical `(pm_version, table_size)` — this project's own
philosophy treats that as one source, not a per-SKU confirmation, so every
inherited block starts in `provisional_blocks`/`provisional_globals` rather
than CONFIRMED. Two were spot-checked live and back the inheritance up:

| Field | PM-table reading | Independent reference | Delta |
|---|---:|---:|---:|
| `tctl` (`d[11]`) | 64.4 °C | `k10temp` Tctl: 65.1 °C | 0.7 °C |
| `ccd_l3_temperature` (`d[448]`) | 49.7 °C | `k10temp` Tccd1: 52.5 °C | 2.8 °C |

`fclk`/`uclk`/`mclk` (`d[71]`/`d[75]`/`d[79]`) read 2000/3000/3000 MHz, consistent
with a 1:1 UCLK:MCLK DDR5-6000 configuration. Neither spot-check is the
differential-load protocol the 9800X3D map itself uses (e.g. the L3 cache-thrash-
vs-ALU comparison) — a single instantaneous reading is corroborating evidence,
not independent confirmation, hence the fields stay HIGH rather than CONFIRMED.

## SMU write profile

### Power limits — validated

`research/dangerous/probe_tdc_edc_9600x.py` (adapted from the 9800X3D's
`probe_tdc_edc.py`) ran the same write/read-back method live: write a distinctive
value on one message ID, read back which PM-table field moved.

| Sent | PM-table field that moved |
|---|---|
| `0x3E` <- 151 W | `d[2]` PPT |
| `0x3D` <- 111 A | `d[63]` **EDC** |
| `0x3C` <- 111 A | `d[8]` **TDC** |

Same mapping as both other Granite Ridge parts. All three limits restored
cleanly to this machine's live baseline (200 W / 130 A / 225 A — a BIOS/PBO
configuration, not a claimed stock spec for this SKU) with no warnings.
`ppt_write_bounds`/`tdc_write_bounds`/`edc_write_bounds` in the profile are
scoped to exactly what was exercised: `151-200 W` / `111-130 A` / `111-225 A`.
`stock_ppt`/`stock_tdc`/`stock_edc` are intentionally left at `0`
(disabling the CLI's "Reset All Settings") since no official stock spec for
this SKU/BIOS configuration has been measured.

### Curve Optimizer — validated, non-obvious command format

Curve Optimizer read-back (RSMU `0xD5`, `GetDldoPsmMargin`) matched this
machine's known BIOS-configured per-core margins across all six cores on the
first try. The write side did not:

1. The legacy per-core mapping the 9800X3D uses (`0x50 + SMU slot`) returned
   `RSP=1` ("accepted") but never actually moved the PSM margin, reproducibly.
2. Three access-restriction hypotheses were tested and ruled out one at a
   time, all with the same negative result: BIOS PBO/Curve Optimizer mode
   (Auto -> Manual), Secure Boot (enabled -> disabled), and kernel lockdown
   (confirmed `[none]`, i.e. not the cause even before testing further).
3. The actual cause was a different mailbox *format*, not a restriction:
   this chip's SMU firmware (`98.84.0`) is newer than the 9800X3D's
   (`98.75.0`) that `0x50-0x57` was measured on. Like the 9950X3D — also on
   newer firmware — this part uses the packed `0x35` CCD/core-mask command
   instead (`co_mode="packed_core_mask"`, `co_msg=0x35`).

`research/dangerous/probe_co_9600x.py` confirms the packed format by
write/readback: writing SMU slot 6 (Linux core 4, the first real core past the
fused gap) through `0x35` moved only that core's margin, landed exactly on the
requested value, and restored cleanly.

This also exposed a real, previously latent bug: `curve_optimizer_command()`
and `curve_optimizer_read_command()` in `gnr_smu/safety.py` indexed MP1 message
IDs and the RSMU CCD/core mask by raw Linux core index, never through
`profile.slot()`. Invisible on every profile with an identity `core_slots`
mapping (9800X3D, 9950X3D), but wrong here: without the fix, a write to Linux
core 4 or 5 would have addressed SMU slots 4/5 — the fused, inactive ones —
instead of the real slots 6/7. Fixed 2026-09-12 by routing both functions
through `profile.slot()`; `smu_message_supported()`'s legacy-mode ID allowlist
was fixed the same way, since a contiguous `0x50..0x50+cores` range no longer
matches the actual IDs a non-identity profile produces.

Negative Curve Optimizer values can still cause computational instability or a
crash; no software can guarantee a given silicon sample is stable at a
requested undervolt. SMU limits and CO margins are volatile and reset on
reboot, same as every other Granite Ridge profile here.
